AI & Agentic Security2

high Preliminary arXiv cs.CR (AI-security papers only) · Nov 11, 00:00

Coding-agent harnesses are living-off-the-land platforms; paper argues for a deterministic reference monitor

The paper argues that once instructions are injected into retrieved content, a coding harness's own tools (bash, curl, find) become the payload, so security has to come from architecture and permission composition, not from the model. It proposes ActiveSecHarness: a reference monitor with HMAC capability tokens across four rings, a 2D taint lattice with a provenance ledger, and deterministic Ring-0 guards.

What changed
Shows deterministic enforcement can block every attack in its test set with no false positives, where an LLM-as-judge guard was both slow and unusable.
Evidence
PreprintOn 252 fixtures, a qwen3:4b judge refused 98.3% of benign work at 142.3 ms per decision; Ring 0 reached ABR 1.000 and FPR 0.000 in 12.7 μs. A stateless baseline missed 4 of 12 kill chains (ABR 0.667). Authors' own evaluation, abstract only.
Opportunity
A concrete design to borrow for agent platforms: capability tokens for tool calls, taint labels on retrieved content, and stateful checks across a trajectory rather than per command.

Why it matters to you

It gives architecture-level language and numbers for something security reviews of agents keep running into: regex allowlists and LLM judges both fail, while deterministic, stateful policy outside the model holds up.

Learn
  • Reference monitors and capability tokens
  • Taint tracking for LLM context
  • Trajectory-level (stateful) policy checks
  • arXiv cs.CR (AI-security papers only)From Attack Surface to Defense Architecture: Compositional Security for Agentic Coding Harnesses

medium Preliminary arXiv cs.CR (AI-security papers only) · Nov 11, 00:00

BypassGym benchmarks whether AI agents can build loaders that evade real EDR products

BypassGym runs agents against real Windows VMs with EDR installed (on Proxmox VE) and asks them to build a loader that runs C2 shellcode without being blocked or killed. It tests 5 lightweight model backends against 6 EDR products and 3 payloads.

What changed
Defense evasion, a gap in existing offensive-AI benchmarks, now has a measurable harness, and small models already score highly on it.
Evidence
PreprintDeepSeek-V4.1 Flash succeeded in 17 of 18 runs; Bitdefender allowed only 5 of 15 runs through. The abstract does not name the other models or EDRs.
Opportunity
A template for testing your own endpoint controls against agent-generated tooling rather than known samples.

Why it matters to you

If cheap models can iterate on evasion against a live EDR, detection based on known tooling weakens. Testing controls against agent-generated variants, and relying on layers beyond endpoint detection, matters more.

Exceptional Incidents1

high Likely BleepingComputer · Nov 10, 14:31

Compromised Qubole IAM users used customers' trusted roles to raid dozens of AWS accounts

Between October 14 and 26, an attacker used two compromised Qubole IAM users to call STS AssumeRole on otherwise unused roles in customer accounts that trusted a Qubole-associated account. Per Wiz and Sentra, they read Secrets Manager, SSM Parameter Store and Lambda environment variables, validated keys with TruffleHog and downloaded S3 objects, hitting tens of companies; Sentra cites millions of files from one customer. AWS says its services were not compromised and operated as designed.

Why it matters to you

This is a vendor-integration attack path: every role you grant a SaaS provider is a standing credential that someone else holds. Nothing was exploited; the trust policies did exactly what they said, which makes this a design and inventory problem rather than a patching one.

Action

List roles trusted by third-party accounts, remove unused ones, add external IDs and source-network conditions, review CloudTrail AssumeRole activity from October 1, and rotate secrets reachable from any Qubole-trusted role.

Learn
  • Confused-deputy protection with sts:ExternalId
  • Scoping role trust policies by source IP/VPC
  • Detecting dormant-role AssumeRole in CloudTrail
UncertainQubole had not publicly confirmed the breach or explained how its IAM users were compromised; details come from Wiz and Sentra via BleepingComputer.

Go & Engineering1

medium Confirmed Go Vulnerability Database · Nov 10, 21:51

Five Go toolchain bugs let a malicious cgo package inject linker flags or run code at build time

The Go team published five advisories (GO-2026-6848, 6849, 6850, 6852, 6853) for cmd/go, cmd/cgo, cmd/compile and cmd/link. Crafted //go:cgo_* directives, escaped quotes in //go:cgo_ldflag, '#cgo pkg-config:' arguments, PE DLL names and .syso or linker input files could each bypass flag validation and reach the external linker, up to arbitrary code execution at build time. Fixed in Go 1.27.4 and 1.26.11.

Why it matters to you

Go's promise that building code doesn't run it rests on cgo flag allowlists, and this batch shows several ways around them. Anywhere that builds third-party modules (CI, dependency scanners, build services) should treat a build as running untrusted code.

Action

Upgrade toolchains in CI and build images to 1.27.4 / 1.26.11, and isolate builds of untrusted modules.
